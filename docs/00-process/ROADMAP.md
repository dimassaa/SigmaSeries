# ROADMAP — что и в каком порядке делается до защиты

> v0.1 · 2026-10-09. План работ **агента**. План работ автора — в `PLAN.md` §9 и §4a.
> Определение «100%» из `PLAN` §1 сюда не входит: оно измеряет полноту спецификации и не ловит отсутствие артефактов. Готовность к защите считается отдельно — `07-kp/COMPLIANCE-BLANK.md`.

## Кто что делает

| Зона | Кто |
|---|---|
| Спеки, модель данных, архитектура и стек, ADR, набор для агента, код P0 | **агент** |
| Пояснительная записка, IDEF0, UML, плакаты, схемы, руководства, листинги, отчёт «Антиплагиат» | **автор** |
| Письмо руководителю | автор отправляет, агент готовит черновик |

Всё, что авторское, сюда сознательно не внесено. Планировать работу над этими артефактами — значит тратить время на чужую зону.

## Решения, принятые до составления плана

Их нельзя выводить из спецификации — исполнитель обязан знать:

- **Продукт не сокращаем.** A/B-тестирование удалено, вся остальная функциональность сохраняется: дашборды аналитика остаются, роль аналитика остаётся, рекомендации (M11) и Wrapped (M7) остаются. Решение автора 2026-10-09 вопреки оценке объёма.
- **Буквы `EC-` закреплены за новыми модулями**, иначе они столкнутся с существующими: M0 → `EC-O` (оболочка), M5 → `EC-U` (UGC), M6 → `EC-H` (главная), M7 → `EC-W` (wrapped), M8 → `EC-N` (аналитика), M9 → `EC-B` (backoffice), M11 → `EC-M` (модель). Занято и остаётся: R, C, D, I, K, S, A, T, V.
- **Новые фичи нумеруются внутри своего модуля**: `F-00-01`, `F-05-01`, `F-06-01`, `F-09-01`, `F-07-01`, `F-08-01`, `F-11-01`.
- **Новые экраны продолжают с `S-85`**, компоненты оболочки — с `UI-14`.
- **`OP-13` (A/B) выводится из реестра**, операций остаётся 17, P0 — по-прежнему 11 при пороге Бланка 10.
- Шаблон фичи — 20 измерений из `PLAN` §5. Измерения 11–16 описываются **только** таблицей «Сквозное качество» в начале модуля, не внутри фичи.
- Метки: `[ГИПОТЕЗА]` — автор ещё не подтвердил; `[проверить в Фазе N]` — требует замера или первоисточника. Без метки утверждение подаётся как решённое.
- Ссылка «Бланк, C-NN» неверна: `C-NN` — идентификатор из `PLAN` §2.1, а не из задания. Писать `PLAN` C-NN.

## Ёмкость

С 9 октября до защиты 62–72 дня. Спецификация и архитектура — фазы 1–4 плана — по оценке 7–11 дней работы агента, код начинается раньше срока «2 ноября» только если фазы 0–4 идут без возвратов.

**Главный риск по объёму не в спецификации, а в коде.** 57 P0-фич и 60 экранов за четыре недели силами агента — оценка не подтверждена ничем, кроме намерения. Если в начале ноября окажется, что код не укладывается, это повод вернуться к вопросу объёма, а не сокращать спецификацию.

### Задача 3. Написать недостающие справочники

**Файлы:** создать `01-product/ROLES-PERMISSIONS.md`, `01-product/VISION.md`, `00-process/GLOSSARY.md`.

На них ссылаются восемь мест в уже написанных спеках; два из них — в шапках, то есть спека сейчас ссылается на несуществующий документ как на источник правила.

**`ROLES-PERMISSIONS`** — самый важный из трёх, потому что в нём живут определения `EC-R1…EC-R8`, которых больше нигде нет. Восемь строк:

| ID | Ситуация | Поведение |
|---|---|---|
| EC-R1 | Роль снята или аккаунт забанен посреди работы с формой | Отправка отклоняется (403), черновик не теряется |
| EC-R2 | Два админа правят одну карточку | Оптимистичная блокировка: второй видит конфликт и сравнение |
| EC-R3 | Админ архивирует сериал, на который ссылаются баннер, подборка, списки, отзывы | Ссылки остаются; сериал скрыт с главной; в списках — «снят с публикации» |
| EC-R4 | Редактор мьютит админа или другого редактора | Запрещено |
| EC-R5 | У пользователя несколько доп. ролей | Права складываются; интерфейс показывает разделы по объединению |
| EC-R6 | Зритель удаляет аккаунт с отзывами и руководствами | Анонимизация автора; опционально — удалить материалы вместе с аккаунтом |
| EC-R7 | Попытка повышения прав через подмену идентификатора в запросе | Права берутся из сессии на сервере, не из тела запроса |
| EC-R8 | Админ вручную правит поле, которое потом перезапишет импорт | Ручное значение блокируется от перезаписи; в студии видно происхождение поля |

Плюс §1 — краткая модель ролей, которую вставляет `context-pack.mjs` в каждый пакет, и §2 — **матрица «роль × объект × действие» без пустых клеток**. Это одно из семи условий «100%» из `PLAN` §1, и файла не существует вовсе. Матрица — таблица, строки: роли, столбцы: объекты (`Сериал`, `Сезон/серия`, `Отзыв`, `Руководство`, `Обсуждение`, `Оценка`, `Отметка просмотра`, `Закладка`, `Подборка`, `Баннер`, `Кадр заставки`, `Жанр/справочник`, `Пользователь`, `Импорт`, `Резервная копия`, `Экспорт`), значения: `—`, `чтение`, `своё`, `все`, `модерация`, `системное`.

**`GLOSSARY`** — таблица из четырёх столбцов, потому что `context-pack.mjs` ищет глоссы по первому столбцу и вставляет её в пакеты. Термины: сериал, сезон, серия, эпизод, жанр, подборка, «выходит», «ждём сезон», отметка просмотра, закладка, спойлер, UGC, модерация, трей, тихие часы, канонический URL. Язык описания — русский: подписи на схемах по требованию Бланка 3.5.

**`VISION`** — два-три абзаца: проблема, для кого, чем этот сервис отличается от существующих. Основа — `input/spec.md`, без новых идей.

**Проверка:** `python3 ../tools/docs-build/build_registries.py` из `docs/` печатает `Ссылки сходятся, пустых измерений нет` и завершается с кодом 0. До этого момента он печатает `Нет определения EC: EC-R1…` — это правильное поведение, а не поломка.

### Задача 8. Модель данных и схема БД

**Файлы:** создать `04-data/DOMAIN-MODEL.md`, `04-data/DATABASE.md`, `04-data/SEED-AND-SIMULATION.md`, `04-data/RETENTION.md`.

**Это самая высокая отдача на единицу усилий во всём плане.** Сущности `E-` уже названы — 40 штук в `MODULES`, — и распределены по модулям. Не хватает полей, типов, ограничений, индексов, правил ссылочной целостности и решений по `G-10`.

**Проверка:** скрипт генерации выполняется на чистой базе без ошибок; количество таблиц и ограничений совпадает с `DOMAIN-MODEL`.

### Задача 9. Стек и архитектура

**Файлы:** создать `05-architecture/STACK.md`, `05-architecture/ARCHITECTURE.md`, `05-architecture/adr/ADR-*.md` (первое — «MVC или MVP»).

Стек ограничен Бланком: Node.js + Express, бизнес-логика на JavaScript, TypeScript отклонён (DEC-017). Версии берутся из документации на дату сдачи, а не по памяти — `C-13` требует актуальных версий.

Планирует короткие эксперименты на рискованных местах, потому что каждый из них дешёвый сейчас и дорогой после: разворот rail без подёргиваний раскладки, стеклянные слои поверх изображения с запасным вариантом без `backdrop-filter`, поиск по словарю на русском и английском без внешних сервисов, отдача картинок из БД с кэш-заголовками, серверный рендеринг или SPA при двуязычных маршрутах.

Каждое решение — с обоснованием, отвергнутыми вариантами и согласованием руководителя; это материал для ПЗ 4.2.2 и 4.2.3.

**Коммит:** `docs: add stack, architecture and ADRs`

## Порядок и почему он такой

Задачи 1–3 идут первыми не потому, что они самые важные по отдельности, а потому, что каждая снимает блокер у всех следующих: письмо определяет, остаётся ли английский интерфейс, и от этого зависит всё в `I18N` и `SEO`; снятие A/B убирает машину состояний и правила, которые иначе придётся согласовывать со спеками; справочники дают спекам источник правил и снимают восемь граничных случаев из реестра.

Задача 8 идёт раньше кода, а не вместе с ним: без схемы БД нельзя написать ни одного запроса, а переделывать их потом дороже, чем написать один раз.

Задачи 6 и 7 P1 отложены сознательно. Они не блокируют код P0, а нехватка времени на них обнаружится в декабре, когда решать будет поздно.

# M9 — Администрирование: глубокая спека

> v0.1 · Фаза 4, партия 7 · P0 (пользователи, бэкап, аудит), P1 (системный мониторинг) · экраны S-70, S-71, S-72, S-81, S-82, S-83 · операции OP-14, OP-16 (совместно с M1), OP-17. Опирается на `ROLES-PERMISSIONS` §2 (матрица прав), `SECURITY` R-SEC-29…36 (аудит, бэкап, удаление), `M1-identity` F-01-09, F-01-10 (мьют, бан, анонимизация), `M5-ugc` F-05-08 (мьют и бан со стороны редактора), `M10-studio` (контент-студия — отделённая часть админки), `M12-import` (запуски, режим защиты), `TESTING` §3. Закрывает G-10 (лёгкое удаление против ссылочной целостности, аудит, двухшаговое подтверждение) и G-11 (что значит «в среднем в сети», как считать, где хранить). Метки: **[ГИПОТЕЗА]**, **[проверить]**. Номера измерений — по `PLAN` §5.

## 0. Сквозное для модуля

**Границы с контент-студией.** Модуль разделён надвое, и деление не по вкладкам, а по ответственности. **M9 — люди и система**: пользователи, роли, ограничения, журнал, бэкап, здоровье. **M10 — контент**: сериалы, подборки, баннеры, кадры, справочники. Обе части — админские разделы, обе открываются из одного раздела «Администрирование», но права проверяются раздельно, и в аудите пишется, какая часть использована.

**Решение G-10 — ключевое для всего модуля.** Требование Бланка 3.3.1 — ссылочная целостность схемы. Отсюда: **физического удаления пользователя не происходит никогда.** Окончательное удаление — это анонимизация: личные поля очищаются, запись остаётся, внешние ключи целы. Это медленнее и оставляет «пользователя удалённого» в базе, но позволяет выполнить требование задания без оговорок, и это единственный способ, при котором каталог, отзывы и оценки остаются валидными. Каскадное удаление каскадом отклонено.

**Анонимизация vs скрытие.** Разные вещи, и их путают чаще всего. **Скрытие** (EC-R3, флажок при бане) убирает материалы из публичного показа, но сохраняет их в базе — вернётся при разбане. **Анонимизация** безвозвратно чистит личные данные, но материалы остаются обезличенными и видимыми. Первое — про модерацию, второе — про запрос пользователя.

**Двухшаговое подтверждение.** Действия, которые нельзя отменить, требуют повторного ввода: удаление окончательно — повторный пароль; бан — число затронутых; массовое действие — список последствий. Правило единое и не зависит от тяжести действия, а от необратимости.

**Аудит пишется всегда и только на чтение.** Записывается: кто, что, когда, на каком объекте, с каким результатом. Сами записи не редактируются, не удаляются и не имеют срока давности. Это единственный способ доказать, что действие было санкционированным, — и он же является требованием безопасности `R-SEC-29`.

**Онлайн — операция OP-14.** «В сети» означает активность за последние 15 минут, а не открытую сессию: сессия может висеть сутки. Показывается **среднее за 24 часа** и **пик**, плюс «сейчас». Хранится агрегат, а не сырые отметки времени: сырые отметки каждого входа за год — это миллионы строк ради одного числа. Среднее считается как сумма почасовых активностей / 24, округление — вниз.

**Сущности (поля уточняет Фаза 5):** E-Restriction (пользователь, вид `mute | ban`, срок, причина, автор, снят, снят_кем) — общая с M5 F-05-08 · E-RoleAssignment (аккаунт, роль, выдал, когда, срок) · E-AuditLog (актор, действие, объект, идентификатор объекта, результат, причина, метаданные до/после, время, IP) — **только чтение** · E-OnlineSample (час, число активных) — агрегат · E-SystemMetric (ключ, значение, время) · E-BackupJob (вид, начало, конец, статус, размер, хеш, проверен) · E-Notification (системные — из M3).

## F-09-01 Список пользователей и фильтры (S-71) · P0

1. **Назначение.** Найти пользователя среди тысяч и понять, что с ним, прежде чем действовать.
2. **Роли.** Администратор.
3. **Триггер.** Переход по адресу раздела «Администрирование» → «Пользователи».
4. **Сценарий.** Таблица: ник, email (частично скрыт для не-админов — здесь только админ), дата регистрации, роль, статус, язык, последняя активность, число оценок, число материалов. Фильтры: период регистрации (от/до), роль (множественный выбор), статус (активен / мьют / бан / удаляется / удалён), язык, «зарегистрирован после», «неактивен дольше N дней», «оценок больше N». Сортировка по любой колонке. Постранично по `admin.user_page_size`.
5. **Альтернативы и ошибки.** Пустой результат — «Никого не нашлось» со сбросом фильтров, а не пустая таблица. Фильтров много и их легко потерять — набор фильтров показывается как строка чипов над таблицей, с кнопкой «сбросить всё». Одновременная работа двух админов — таблица не требует блокировки: это чтение.
6. **Состояния.** Пусто · загрузка · список · отфильтровано · ошибка.
7. **Данные.** E-User (без пароля и без токенов), E-Restriction, агрегаты по оценкам и материалам.
8. **Правила.**
   - (а) Фильтры комбинируются по «и»; внутри одного фильтра значения — по «или».
   - (б) Email показывается частично (`d***@example.com`) даже админу, если тот не ищет по email: это снижает риск утечки при демонстрации экрана. При явном поиске по email результат выводится полностью — искатель и есть админ.
   - (в) Числа агрегируются, а не считаются по таблице: при тысячах пользователей `COUNT` на каждой строке даёт секунды.
   - (г) Удалённые пользователи видны только по явному фильтру статуса — по умолчанию скрыты, чтобы не мешать.
   - (д) Каждая строка — ссылка на карточку (S-72).
9. **Валидация и лимиты.** ≤ 50 строк на страницу; ≤ 10 значений в множественном фильтре; диапазон дат ≤ 5 лет.
10. **Edge cases.** EC-B1, EC-B2, EC-B3.
17. **Побочные эффекты.** Запись в аудит при изменении фильтров — нет (чтение); при переходе в карточку — есть.
18. **Приёмка.** *Дано* 3 412 пользователей; *когда* открыт список; *тогда* 50 строк, счётчик «показано 50 из 3 412», время отклика < 300 мс. *Дано* фильтр «роль = редактор» и «неактивен дольше 30 дней»; *тогда* результат — пересечение, а не объединение. *Дано* фильтры дают пусто; *тогда* «Никого не нашлось» и кнопка сброса, а не пустая таблица.
19. **UI.** Чипы фильтров важнее самой таблицы:

```
┌ Пользователи ────────────────────────────────────────────────┐
│ [период ▾][роль ▾][статус ▾][язык ▾][неактивен ▾] [Сбросить]│
│  ● зарегистрирован с 01.09 ✕   ● роль: редактор ✕            │
│                                                                  │
│ Показано 12 из 3 412                                            │
│ Ник      Email          Регистрация  Роль      Статус  Активен│
│ anna     a***@ex.com    12.09.2026  —         актив   2 ч назад │
│ boris    b***@ex.com    03.08.2026  редактор  мьют   8 дн      │
│ vera     v***@ex.com    21.06.2026  —         удалён  41 дн      │
└──────────────────────────────────────────────────────────────┘
   ↑ чипы показывают активные фильтры: без них легко забыть, что
     список отфильтрован, и сделать вывод по неполным данным
```
   **Фокальная точка:** строка фильтра, не таблица — без неё список не найти. **Телефон:** фильтры в сворачиваемой панели, таблица превращается в карточки. **Планшет:** три колонки вместо семи, остальные — в раскрытии карточки. **Скелетон:** восемь строк, ширина колонок совпадает с боевой.
20. **КП.** Скриншот на плакат «скриншоты окон» — этот экран показывает, что админка существует и работает с данными.

## F-09-02 Карточка пользователя: роли, ограничения, удаление (S-72) · P0

1. **Назначение.** Сделать одно действие администратора за одно подтверждение и одну запись в аудит.
2. **Роли.** Администратор.
3. **Триггер.** Клик по строке в S-71.
4. **Сценарий.** Карточка: данные, история материалов, история решений редактора (если роль есть), активные ограничения, выданные роли. Действия: «Выдать роль», «Снять роль», «Мьют», «Бан», «Удалить окончательно». Каждое — с обязательной причиной. «Удалить окончательно» дополнительно требует **повторный пароль администратора** и показывает перечень последствий до подтверждения.
5. **Альтернативы и ошибки.** Действует на себя — «Удалить себя» заблокировано, объяснение в тексте кнопки. Последний админ — «Снять роль» заблокировано. Пользователь уже забанен — повторный бан предлагает снять, а не добавить второй. Снятие роли во время его использования — сессия не продлевается (EC-R11).
6. **Состояния.** Активен · мьют · бан · удаляется (14 дней) · удалён · роли выданы.
7. **Данные.** E-User, E-Restriction, E-RoleAssignment, E-AuditLog.
8. **Правила.**
   - (а) Ни одно действие не выполняется без причины, и причина сохраняется вместе с действием в аудите.
   - (б) Удаление окончательное: 14 дней между запросом и анонимизацией (`admin.delete_grace_days`); в этот период вход отменяет удаление (M1 F-01-10). **Повторный пароль требуется в момент запроса удаления, не в момент фактической анонимизации.**
   - (в) При удалении материалы и оценки **остаются обезличенными**, если админ не выбрал «удалить материалы вместе с аккаунтом» (EC-R6, H-61).
   - (г) Админ не может удалить админа молча: действие видно в аудите с указанием, кто и почему.
   - (д) Все действия карточки записываются в аудит **до** выполнения, с результатом после — так, чтобы сбой не оставлял действия без следа.
9. **Валидация и лимиты.** Причина ≤ 500 знаков; срок мьюта — из `ugc.mute_min_h`…`mute_max_h`; срок бана — не ограничен для админа.
10. **Edge cases.** EC-B4, EC-B5, EC-R1, EC-R4, EC-R11.
17. **Побочные эффекты.** Отзыв сессий при бане; сброс кэшей профиля; событие администратору о бане.
18. **Приёмка.** *Дано* два админа; *когда* один пытается снять роль второго; *тогда* действие заблокировано с объяснением «последний администратор». *Дано* админ удаляет пользователя; *тогда* требуется повторный пароль, показан перечень последствий, запись создаётся со статусом «Удаляется», а через 14 дней — анонимизация. *Дано* пользователь входит на 5-й день; *тогда* удаление отменяется, и это пишется в аудит.
19. **UI.** Действия внизу карточки, разрушающее — отдельно и не первым:

```
┌ anna ────────────────────────────────────────────────────────┐
│  a***@ex.com · с 12.09.2026 · RU                            │
│  Оценок 24 · Материалов 3 · Активность: 2 ч назад           │
│  Роли: —        Ограничения: нет                             │
│  ─────────────────────────────────────────────────────────   │
│  [ Выдать роль ▾ ]  [ Мьют ]  [ Бан ]                       │
│                                                                  │
│  ─── Опасная зона ─────────────────────────────────────────   │
│  Удалить окончательно. Данные будут обезличены через 14 дней.│
│  Материалы и оценки сохранятся без имени.                     │
│              [ Удалить окончательно ]                         │
└──────────────────────────────────────────────────────────────┘
```
   **Фокальная точка:** блок «опасная зона» отделён и не смешан с обычными действиями. **Телефон:** действия в столбик, «опасная зона» — под ними, с разделителем. **Скелето��:** четыре блока строк.
20. **КП.** Диаграмма состояний аккаунта (`STATES` §2) с переходом в удаление.

## F-09-03 Журнал аудита (S-83) · P0

1. **Назначение.** Сделать каждое административное действие доказуемым и найти, кто что сделал.
2. **Роли.** Администратор — только чтение.
3. **Триггер.** Раздел «Администрирование» → «Журнал».
4. **Сценарий.** Таблица по убыванию времени: время, актор, действие, объект, результат, причина. Фильтры: период, актор, тип действия, результат, объект. Клик по строке раскрывает метаданные «до» и «после», если действие их меняло.
5. **Альтернативы и ошибки.** Запись ссылается на объект, который уже удалён (пользователь анонимизирован) — строка остаётся, показывается «объект удалён», не битая ссылка. Журнал пуст (первый запуск) — «Ещё нет действий». Фильтр по периоду без результатов — пустое состояние со сбросом.
6. **Состояния.** Пусто · список · детали строки · фильтр.
7. **Данные.** E-AuditLog. **Только чтение: API не имеет методов записи из интерфейса и не имеет их вообще — запись только из прикладного кода.**
8. **Правила.**
   - (а) Записи не удаляются и не редактируются. Нет роли, которая это может (`ROLES-PERMISSIONS` §2: админ — «Ч»).
   - (б) Хранятся бессрочно. Ротация журнала не предусмотрена: объём за учебный проект измеряется десятками тысяч строк.
   - (в) Причина обязательна в самой записи, а не только в интерфейсе — иначе причина потеряется при выгрузке.
   - (г) Метаданные «до/после» не содержат секретов: пароли, токены и ключи не пишутся в аудит ни при каких условиях (`R-SEC-33`).
   - (д) Выгрузка журнала — CSV без идентификаторов сессий и токенов.
9. **Валидация и лимиты.** Постранично 100; выгрузка ограничена 50 000 строк за раз.
10. **Edge cases.** EC-B6, EC-B7.
17. **Побочные эффекты.** Ни одного: журнал только читается.
18. **Приёмка.** *Дано* админ забанил пользователя; *когда* открыт журнал; *тогда* есть запись с актором, причиной, объектом и результатом, и она **не удаляется** даже при последующем удалении самого админа. *Дано* действие меняло поле; *тогда* в деталях видно «до» и «после». *Дано* в метаданных было поле с секретом; *тогда* его в записи нет.
19. **UI.** Таблица времён, детали — раскрытием строки:

```
┌ Журнал ──────────────────────────────────────────────────────┐
│ [период ▾][актор ▾][действие ▾][результат ▾]                │
│                                                               │
│ 2026-10-09 15:04  admin  бан           → anna     успешно   │
│                       причина: флуд отзывов                  │
│ 2026-10-09 14:31  admin  роль+админ    → petr     успешно   │
│ 2026-10-09 11:02  admin  удалить       → vera     отказ:    │
│                       пользователя            сам          │
│ 2026-10-08 19:44  admin  бэкап         → job #31  успешно   │
└───────────────────────────────────────────────────────────────┘
   ↑ отказ — такая же строка, как успех: важно видеть, что действие
     не состоялось, и по какой причине
```
   **Фокальная точка:** время и действие в одной строке — журнал читают по времени. **Телефон:** карточки, каждое действие — отдельная. **Скелетон:** восемь строк таблицы.
20. **КП.** Скриншот на плакат «скриншоты окон».

## F-09-04 Резервные копии и проверка восстановления (OP-17) · P0

1. **Назначение.** Сделать данные восстановимыми и доказать, что восстановление работает.
2. **Роли.** Планировщик — по расписанию; администратор — ручной запуск и проверка.
3. **Триггер.** `backup.schedule` ежедневно; либо кнопка «Создать копию».
4. **Сценарий.** Ночная копия: дамп базы плюс файлы изображений из БД (C-04: изображения хранятся в БД, значит одна копия покрывает всё). После создания — **пробное восстановление во временную базу** и проверка целостности. Копия получает статус «Проверена» только после этого. Хранятся последние `backup.keep_last`.
5. **Альтернативы и ошибки.** Копия создана, но проверка не прошла — статус «Ошибка», бэкап считается негодным, администратор видит предупреждение, следующая копия не удаляет предыдущую исправную. Место кончилось — копия не создаётся, оповещение администратора, **предыдущие исправные копии не трогаются**. Приложение выключено в момент расписания — копия создаётся при следующем старте (M3 F-03-07 использует тот же приём).
6. **Состояния.** Запланирована · идёт · создана · проверяется · проверена · ошибка · устарела (копия не проверялась дольше суток).
7. **Данные.** E-BackupJob (вид, начало, конец, статус, размер, хеш файла, проверен); путь хранения — вне БД, на диске; шифрование файла — по `R-SEC-25`.
8. **Правила.**
   - (а) «Проверена» означает фактически выполненное восстановление, а не запись в лог об успешном завершении. Это единственный способ отличить работающую копию от испорченной.
   - (б) Ротация удаляет только **проверенные** копии. Непроверенная копия никогда не удаляется — иначе сбой проверки приведёт к потере всех копий.
   - (в) Сначала резервная копия, потом ночные задачи (M3 F-12-07 правило): окно расписания не должно пересекаться с тяжёлым дампом.
   - (г) Копия шифруется, доступ к файлам — только администратору (`R-SEC-25`).
   - (д) Восстановление **никогда не на рабочих данных**: проверка идёт во временную базу, переключение на неё — отдельное ручное действие с подтверждением.
9. **Валидация и лимиты.** Минимальный размер копии — 10% от размера базы, меньше считается ошибкой **[ГИПОТЕЗА]**; RPO 24 ч, RTO 2 ч — целевые, не гарантированные.
10. **Edge cases.** EC-B8, EC-B9, EC-B10.
17. **Побочные эффекты.** Запись в аудит; нагрузка на диск во время дампа; уведомление администратору при ошибке.
18. **Приёмка.** *Дано* копия создана; *когда* она проверяется; *тогда* её статус «Проверена» только после фактического восстановления во временную базу. *Дано* проверка не прошла; *тогда* копия не годна и ротация её не тронет. *Дано* админ нажал «Восстановить из копии»; *тогда* требуется повторный пароль и показан список того, что будет потеряно с момента копии.
19. **UI.** Статус копии важнее её размера:

```
┌ Резервные копии ─────────────────────────────────────────────┐
│  Последняя: сегодня 03:30 · проверена · 1,42 ГБ              │
│  Следующая: завтра 03:30                                      │
│  ⚠ Копия от 07.10 не проверена — 2 дня                        │
│                                                               │
│  [ Создать копию сейчас ]  [ Восстановить ]                  │
│                                                               │
│  Дата        Размер    Статус        Действие                  │
│  09.10 03:30  1,42 ГБ  ✓ проверена   [ Восстановить ]        │
│  08.10 03:30  1,41 ГБ  ✓ проверена   [ Восстановить ]        │
│  07.10 03:31  1,40 ГБ  ⚠ не проверена [ удалить нельзя ]     │
│                                                               │
│  Хранятся 7 последних. Удаляются только проверенные.          │
└───────────────────────────────────────────────────────────────┘
```
   **Фокальная точка:** строка последней копии и её статус — это ответ на вопрос «данные в безопасности». **Телефон:** карточки вместо таблицы. **Скелтон:** четыре строки. **Почему «удалить нельзя»:** это осознанное ограничение, а не ошибка интерфейса.
20. **КП.** Диаграмма деятельности «резервное копирование и проверка».

## F-09-05 Онлайн: сейчас, среднее, пик (OP-14) · P0

1. **Назначение.** Ответить на вопрос «сколько сейчас в сети в среднем», не собирая сырые логи.
2. **Роли.** Система считает; администратор видит.
3. **Триггер.** Активность пользователя (запрос к API от аутентифицированной или анонимной сессии); агрегат пересчитывается раз в минуту.
4. **Сценарий.** Раз в минуту система записывает, сколько пользователей имели активность в последние 15 минут. Хранится ряд почасовых значений (96 точек на 4 суток). Админ видит: «сейчас» (текущее окно), «среднее за 24 часа», «пик за 24 часа» и график по часам.
5. **Альтернативы и ошибки.** Приложение выключено в момент расчёта — значение за пропущенный час не заполняется, в графике разрыв, а не ноль: **ноль был бы ложью**. При первом запуске агрегатов графика нет — «Данные появятся после первого часа работы». Ночной перезапуск приложения создаёт разрыв в 03:30 — принимается.
6. **Состояния.** Нет данных · мало данных (< 6 часов) · норма · ночной разрыв.
7. **Данные.** E-OnlineSample (час, зарегистрированные, гости) — агрегат в базе, не в памяти; сырые отметки активности не хранятся.
8. **Правила.**
   - (а) «Онлайн» = активность за последние 15 минут, а не открытая сессия: сессия живёт месяц и так считать нельзя.
   - (б) Считаются **уникальные пользователи**, а не сессии: один человек с четырьмя вкладками — один.
   - (в) Анонимные посетители считаются отдельно от зарегистрированных; обе цифры показываются, и это снимает вопрос «откуда столько гостей».
   - (г) Среднее — сумма часовых значений / 24, округление вниз.
   - (д) Агрегат не обнуляется при перезапуске приложения: он живёт в базе, а не в памяти.
9. **Валидация и лимиты.** График за 4 суток; более старые данные — среднее по суткам.
10. **Edge cases.** EC-B11, EC-B12.
17. **Побочные эффекты.** Одна запись в минуту, рост базы минимален; агрегат сбрасывается при смене суток.
18. **Приёмка.** *Дано* в 15-минутном окне активны 40 уникальных пользователей в 90 вкладках; *тогда* «сейчас» = 40. *Дано* приложение было выключено с 02:00 до 04:00; *тогда* на графике разрыв, а не нулевая точка. *Дано* данные за 2 часа; *тогда* «мало данных» и среднее не показывается.
19. **UI.** Три крупных числа и график — то, что просили «сколько в сети в среднем»:

```
┌ Онлайн ──────────────────────────────────────────────────────┐
│  Сейчас        Среднее за 24 ч     Пик за 24 ч                 │
│    128              94                231                     │
│    ↑ три крупных числа, 60-30-10: цифры ~10% площади          │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  ▁▂▃▅▇█▇▅▃▂▁▂▃▄▆█▇▅▃▂▁▁▂▃▅▇█▇▅▃▁  ← 4 суток по часам  │    │
│  │  ↑ разрыв = приложение было выключено, не ноль          │    │
│  └──────────────────────────────────────────────────────────┘    │
│  Зарегистрированных 96 · гостей 32                              │
└────────────────────────────────────────────────────────────────┘
```
   **Фокальная точка:** «Сейчас» — слева и крупнее остальных. **Телефон:** три числа в строку, график ниже. **Скелтон:** три блока-числа и прямоугольник графика.
20. **КП.** Скриншот на плакат «скриншоты окон»; OP-14 — в ПЗ 4.1.2.

## F-09-06 Здоровье системы (S-82) · P1

1. **Назначение.** Показать, что система работает, и дать точку входа для ручных действий.
2. **Роли.** Администратор.
3. **Триггер.** Раздел «Администрирование» → «Система».
4. **Сценарий.** Обзор: онлайн (F-09-05), ошибки 5xx за час, отклик p95 по каждому маршруту, задержка цикла событий аналитики, очередь модерации и её режим (M5 F-05-03), задачи по расписанию и их последний результат, место на диске, состояние последней резервной копии. Каждая метрика ведёт к источнику: «очередь модерации» — на S-50.
5. **Альтернативы и ошибки.** Метрика недоступна (сбор не идёт) — «нет данных», а не ноль. Метрика в красной зоне — строка подсвечена и стоит первой. Метрик много и они разной важности — порядок: сначала то, что сломано, потом то, что может сломаться.
6. **Состояния.** В норме · есть проблема · часть метрик недоступна · критично.
7. **Данные.** E-SystemMetric, текущие значения очереди и задач.
8. **Правила.**
   - (а) Красное — не цвет, а текст состояния: «очередь растёт», «бэкап не проверялся 2 дня» (`R-A11Y-19`).
   - (б) Метрика без источника не показывается: число, которое нельзя проверить, мешает.
   - (в) Никаких действий, кроме перехода в соответствующий раздел и запуска задачи, — экран наблюдает, а не управляет.
   - (г) Кнопка «проверить восстановление» есть прямо здесь, продублирована из F-09-04: это единственное действие, которое админ делает с кнопки.
9. **Валидация и лимиты.** Графики за 24 часа; детализация до часа.
10. **Edge cases.** EC-B13.
17. **Побочные эффекты.** Сброс кэша метрик раз в минуту.
18. **Приёмка.** *Дано* очередь модерации в «осторожном» режиме; *тогда* строка первая, с текстом «растёт», и ведёт на S-50. *Дано* сбор метрики недоступен; *тогда* «нет данных» и не ноль.
19. **UI.** Порядок определяется состоянием, а не фиксирован:

```
┌ Система ─────────────────────────────────────────────────────┐
│ ⚠ Очередь модерации растёт: 48 мин разбора      → открыть   │
│ ⚠ Резервная копия не проверялась 2 дня          → открыть   │

│  Ошибки 5xx      2 за час       в норме                        │
│  Отклик p95      140 мс         в норме                        │
│  Задачи          все выполнены  в норме                        │
│  Место на диске  41% свободно   в норме                        │
│  Цикл событий    12 с задержка  в норме                        │
└───────────────────────────────────────────────────────────────┘
```
   **Фокальная точка:** первая проблема, а не первая строка. **Телефон:** список, каждая метрика — строка, проблемные первыми. **Скелето��:** шесть строк высотой строки.
20. **КП.** Скриншот на плакат «скриншоты окон».

## F-09-07 Роли: выдача и снятие · P0

1. **Назначение.** Дать администратору выдать и снять служебные права без правки базы вручную.
2. **Роли.** Администратор.
3. **Триггер.** Карточка пользователя (S-72) → «Выдать роль»; раздел → «Роли».
4. **Сценарий.** Выбор роли, срок (бессрочно или до даты), необязательная заметка. Подтверждение. Роль действует немедленно: следующая проверка прав её видит. Снятие — с указанием причины; у последнего администратора заблокировано. Список ролей: кто, какая, кто выдал, когда, до какой даты.
5. **Альтернативы и ошибки.** Некому выдать роль (последний админ) — блокировка с объяснением. Роль уже выдана — «продлить», а не создать вторую. Срок роли истёк — роль снимается автоматически, в аудите строка «истекло», а не «снял человек». Аккаунт не подтвердил email — роль выдать нельзя (EC-R10).
6. **Состояния.** Нет ролей · есть постоянные · есть срочные · просрочена.
7. **Данные.** E-RoleAssignment, E-User.
8. **Правила.**
   - (а) 2FA обязательна до выдачи роли (DEC-015): без неё роль выдаётся, но с предупреждением и сроком не более 7 дней **[ГИПОТЕЗА]**.
   - (б) Истечение срока — полноценное снятие с записью в аудите, различие только в формулировке причины.
   - (в) Выдача и снятие ролей пишутся в аудит как отдельные события, не как часть правки пользователя.
   - (г) Роль не наследуется: права не переходят по приглашению или по ссылке.
9. **Валидация и лимиты.** Не более 3 активных ролей на аккаунт; заметка ≤ 300 знаков.
10. **Edge cases.** EC-B14, EC-R10.
17. **Побочные эффекты.** Пересчёт кэша прав; уведомление пользователю о выдаче и снятии.
18. **Приёмка.** *Дано* аккаунт без подтверждённого email; *когда* админ выдаёт роль; *тогда* действие заблокировано (EC-R10). *Дано* роль выдана на 7 дней; *когда* срок истёк; *тогда* роль снята автоматически, в аудите причина «срок истёк». *Дано* два админа; *когда* один снимает роль другого; *тогда* блокировка «последний администратор».
19. **UI.** Роль — это строка, а не галочка: у каждой есть срок и автор:

```
┌ Роли ────────────────────────────────────────────────────────┐
│  Выдать роль: [редактор ▾]  до [ бессрочно ▾]  заметка [   ] │
│                                    [ Выдать ]                 │
│                                                               │
│  Ник       Роль       Кто выдал   Выдана     Действует до     │
│  petr      админ      admin       09.10      бессрочно       │
│  sasha     аналитик   admin       05.10      12.10            │
│                                                               │
│  ⚠ Последний администратор не может быть снят.               │
└───────────────────────────────────────────────────────────────┘
```
   **Фокальная точка:** форма выдачи сверху. **Телефон:** карточки. **Скелетон:** три строки.
20. **КП.** Скриншот на плакат «скриншоты окон».

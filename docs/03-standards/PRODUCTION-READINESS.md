# PRODUCTION-READINESS — чек-лист готовности и «о чём не знают вайбкодеры»

> v0.2 · Фаза 3, не пересматривался после неё. Источники: ваши материалы «Что сделать перед завершением проекта» и «О чём не знают вайбкодеры».
> Цели: (1) каждый пункт либо входит в требования, либо осознанно отклонён с обоснованием — это материал для ПЗ 4.2.3; (2) всё, что проверяется инструментом, уходит в автоматические проверки и в AGENTS (Фаза 8). Конкретные инструменты выбираем в Фазе 7.
> **Из 18 пунктов проверки 6 ссылаются на файлы Фаз 5 и 7** (`STACK`, `ARCHITECTURE`, `DATABASE`, `ROLES-PERMISSIONS`), которых ещё нет. Пока их нет, чек-лист нельзя пройти.

## 1. Чек-лист перед защитой (18 пунктов)

| № | Пункт | Что проверяем конкретно | Как | Куда в spec |
|---|---|---|---|---|
| 1 | Лишние пакеты | Нет неиспользуемых зависимостей | Автопроверка в CI | `STACK` |
| 2 | Секреты в git | Ключи (TMDB, БД, сессии) нет ни в коде, ни в истории | Сканер секретов по истории | `SECURITY` |
| 3 | Ограничение частоты | Лимиты на вход, регистрацию, отправку материалов, поиск, API; отдельно для гостей | Тесты | M1, M5 |
| 4 | Права доступа | Проверка на сервере на каждый запрос; тесты «чужой объект» (IDOR) | Тесты по матрице ролей | `ROLES-PERMISSIONS` |
| 5 | Хеширование паролей | Стойкий алгоритм с солью и параметрами; пароли не попадают в логи | Ревью + тест | M1 |
| 6 | Ключи API | Только в окружении; клиенту не отдаются; запросы к TMDB — только с сервера | Сканер + ревью | M12 |
| 7 | Аутентификация | Срок жизни и отзыв сессий, 2FA служебных, защита от перебора, подтверждение email, сброс пароля | Тесты | M1 |
| 8 | Обновление зависимостей | Актуальные версии без известных уязвимостей (Бланк C-13) | Аудит зависимостей | `STACK` |
| 9 | Формы | Валидация на сервере (длины, форматы), экранирование, ограниченная разметка | Тесты | M4, M5 |
| 10 | XSS | Вывод экранируется, CSP, безопасная разметка руководств и спойлеров | Тесты + заголовки | `SECURITY` |
| 11 | Режим отладки | Выключен в «боевом» режиме; нет трассировок стека клиенту | Проверка конфигурации | `ARCHITECTURE` |
| 12 | Переменные окружения | Полный список; безопасные значения по умолчанию; без обязательных переменных приложение не стартует | Проверка при старте | `ARCHITECTURE` |
| 13 | Открытые файлы | Не раздаются `.env`, исходники, дампы БД, бэкапы, служебные каталоги | Тест запросами | `SECURITY` |
| 14 | Админские маршруты | Роль + 2FA + повторный пароль для опасных действий; отдельные лимиты | Тесты | M9 |
| 15 | Защита API | Аутентификация и авторизация, валидация, ограничение размера тела, единый формат ошибок без утечек | Тесты | `SECURITY` |
| 16 | CORS | Разрешён только свой источник; никакого `*` вместе с куками | Тест | `SECURITY` |
| 17 | Заголовки безопасности | CSP, HSTS (при HTTPS), запрет угадывания типа, политика реферера, запрет встраивания | Проверка ответов | `SECURITY` |
| 18 | Доступ к БД | Отдельный пользователь с минимальными правами, параметризованные запросы, недоступна снаружи, шифрованное соединение, бэкапы зашифрованы | Ревью + тест | `DATABASE` |

## 2. Темы из списка «о чём не знают вайбкодеры» — что применяем

| Тема | Решение | Где и как |
|---|---|---|
| Ограничение частоты, backpressure, защита от перегруза | **Применяем** | Антиспам M5: лимиты по пользователю, IP, устройству; очередь с потолком; вход и поиск |
| Таймауты, повторы, экспоненциальная задержка, идемпотентность, circuit breaker (лёгкий) | **Применяем** | M12 (TMDB), двойная отправка форм, уведомления |
| Кэширование и инвалидация | **Применяем** | Главная (баннеры раз в сутки), изображения (долгий кэш + версия), справочники; инвалидация при правках админа |
| Индексы, оптимизация запросов, N+1, пул соединений | **Применяем** | `DATABASE`; бюджет запросов на страницу |
| Миграции, версионирование схемы | **Применяем** | Миграции вверх и вниз; скрипт создания БД — приложение к ПЗ |
| Партиционирование | По необходимости | Таблица событий аналитики, если объём вырастет |
| Состояния гонки, оптимистичные блокировки | **Применяем** | Один отзыв и одна оценка на пользователя (уникальные ограничения), правка карточек двумя админами, счётчики голосов |
| Пессимистические и распределённые блокировки | Нет | Один экземпляр сервера |
| Cron-задачи | **Применяем** | Синхронизация, баннеры дня, рассылка уведомлений, агрегаты онлайна и аналитики, бэкап |
| Очереди сообщений, очередь недоставленных | **Применяем в малом** | Очередь проверок, уведомлений, импорта + таблица неудачных задач; брокер — решение Фазы 7 |
| SSE / WebSockets / long polling | **Применяем одно** | Уведомления и онлайн; выбор в Фазе 7 (SSE проще) |
| Мониторинг, логи, метрики, алерты, health checks, SLO / SLI | **Применяем в малом** | Страница состояния у админа (p95, ошибки, очередь, задачи, онлайн); проверка живости; цели в числах — `PERFORMANCE`. Распределённая трассировка — нет |
| Секреты, TLS, шифрование в канале и на диске, CORS, CSRF, XSS, SQL-инъекции, SSRF | **Применяем** | `SECURITY`. SSRF: загрузчик картинок ходит только на разрешённые адреса TMDB |
| WAF, защита от DDoS | Позже | При публикации в интернет — за обратным прокси или сервисом защиты |
| Feature flags, откаты | **Применяем** | Флаги = эксперименты A/B и включение функций уровня P1; откат = миграции вниз + возврат версии |
| CI/CD, Docker, IaC | По решению Фазы 7 | CI: линт, тесты, аудит зависимостей. Docker — если нужен для БД и кэша на Windows. Terraform / Helm — нет |
| Резервные копии, аварийное восстановление | **Применяем** | Плановый бэкап + шифрование + **проверка восстановления** (Бланк 3.3.4) |
| Зависимости, версионирование API | **Применяем** | Lock-файл, аудит; версия API в пути |
| Утечки памяти, сборка мусора, потокобезопасность | Следим | Рост памяти на нагрузочном прогоне; состояние в памяти (корзины лимитов) не делится между процессами |
| Задержка, пропускная способность, P99 | **Применяем** | Цели в `PERFORMANCE`; нагрузочный прогон на сценарии «флуд спама» и «главная» |
| Часы, DNS, TCP/UDP, HTTP/2 и 3, gRPC, webhooks | Частично | Время хранится в UTC, часовой пояс — на показе; остальное по умолчанию сервера |

## 3. Осознанно не применяем (масштаб проекта)

| Тема | Почему не нужно | Когда понадобится |
|---|---|---|
| Kubernetes, service discovery | Один экземпляр на одном компьютере (Windows) | Несколько узлов и автоматическое развёртывание |
| Балансировщик, API-шлюз | Один экземпляр; шлюз нечего объединять | Горизонтальное масштабирование |
| Шардинг, реплики чтения, репликация, выбор лидера | Объём данных — тысячи карточек и сотни тысяч событий | Рост нагрузки на чтение или объёма |
| CAP, eventual consistency, распределённые транзакции, Saga | Один узел и одна БД — строгая согласованность | Разделение на сервисы |
| Несколько регионов, failover | Один регион, демо на локальной машине | Требования к доступности |
| Canary / blue-green / rolling | Один экземпляр | Несколько экземпляров |
| Serverless, cold starts, оптимизация расходов | Хостинга нет | Публикация в облаке |
| Chaos engineering, on-call, постмортемы | Нет эксплуатации | Продуктовая эксплуатация |
| gRPC, Helm, Terraform | Нет межсервисных вызовов и инфраструктуры как кода | Микросервисы и облако |

**Путь роста (для ответа на защите):** приложение без состояния за балансировщиком → общий кэш и очередь вне процесса → реплика БД для чтения → CDN для изображений → разделение импорта, модерации и аналитики на отдельные сервисы.

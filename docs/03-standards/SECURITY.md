# SECURITY — стандарт безопасности

> v0.1 · Фаза 3 · закрывает п. 3.3.4 Бланка (защита хранимых и передаваемых данных, резервное копирование) и раздел ПЗ 4.2.6. Правила `R-SEC-NN` проверяемы и идут в тесты и AGENTS. Угрозы — `THREAT-MODEL`, чек-лист перед защитой — `PRODUCTION-READINESS`. Метки: **[ГИПОТЕЗА]** — стартовое значение.
> Ориентиры (проверены 2026-10-04): **OWASP ASVS 5.0** (вышла в мае 2025) — уровень L1 для всего приложения и L2 для входа, сессий, контроля доступа и админ-функций **[ГИПОТЕЗА]**; риски — **OWASP Top 10:2025** (опубликован 6 ноября 2025).

## 1. Принципы

Запрет по умолчанию · наименьшие привилегии · глубокая защита (несколько слоёв) · внешним данным не доверяем (в том числе TMDB и IMDb) · безопасные значения по умолчанию · секреты вне кода · логи без секретов.

## 2. Правила

### Вход и сессии (M1)
| ID | Правило |
|---|---|
| R-SEC-01 | Пароли: Argon2id с солью, параметры — по актуальной шпаргалке OWASP; длина 10–128; проверка по списку распространённых паролей; без требований «обязательный символ». |
| R-SEC-02 | Сессии на сервере; cookie `HttpOnly; Secure; SameSite=Lax`; идентификатор меняется после входа, смены роли и пароля; отзыв при смене пароля, роли, бане. |
| R-SEC-03 | Сроки **[ГИПОТЕЗА]**: зритель — простой 7 дней, абсолютный 30; служебные роли — простой 30 минут, абсолютный 12 часов. Список устройств с отзывом. |
| R-SEC-04 | 2FA (TOTP, RFC 6238) обязательна для редактора, аналитика, админа (**подтверждено автором**, DEC-015); секрет хранится зашифрованным; резервные коды — только хеши; код не принимается повторно. |
| R-SEC-05 | Перебор: лимиты по аккаунту и IP, нарастающая задержка; блокировка аккаунта только временная (иначе вектор отказа в обслуживании). |
| R-SEC-06 | Одинаковые ответы для «аккаунта нет» и «неверный пароль», для регистрации с занятым email и для сброса; сравнение секретов за постоянное время. |
| R-SEC-07 | Сброс пароля и подтверждение email — одноразовые токены, срок 30 минут, в БД только хеш токена. |
| R-SEC-08 | Возврат после входа — только относительные внутренние адреса (нет открытого перенаправления). |

### Права доступа (все модули)
| ID | Правило |
|---|---|
| R-SEC-09 | Проверка прав на сервере при каждом запросе по `ROLES-PERMISSIONS`; роль берётся из сессии, не из запроса. |
| R-SEC-10 | Проверка владения объектом (нет доступа к чужим закладкам, уведомлениям, черновикам). |
| R-SEC-11 | Белые списки полей при записи (нет массового присвоения). |
| R-SEC-12 | Опасные действия (смена ролей, окончательное удаление, восстановление из копии) — повторный пароль + подтверждение с перечнем последствий + запись в аудит. |

### Ввод и вывод
| ID | Правило |
|---|---|
| R-SEC-13 | Валидация по схеме на сервере: типы, длины, форматы; лишние поля отклоняются; лимит размера тела; нормализация Unicode. |
| R-SEC-14 | Вывод экранируется по контексту. Материалы пользователей — обычный текст; руководства — ограниченное подмножество разметки через проверенный очиститель со списком разрешённых тегов; ссылки в материалах запрещены (в руководствах — только на страницы каталога) — **подтверждено автором**, DEC-015. |
| R-SEC-15 | Данные TMDB и IMDb — недоверенные: экранировать, ограничивать длину, хранить как текст. |
| R-SEC-16 | SQL только параметризованный; динамические имена колонок и сортировок — из белого списка. |
| R-SEC-17 | Изображения (импорт, админ): тип определяется по содержимому, лимит байтов и размеров, перекодирование с удалением метаданных, имена генерируются, хранение в БД. |
| R-SEC-18 | SSRF: загрузчик ходит только на разрешённые домены TMDB; без переходов за их пределы и на частные адреса; таймаут и лимит размера. |
| R-SEC-19 | Пользовательские данные не превращаются в регулярные выражения; словарь модерации ищется автоматом Ахо — Корасик (нет ReDoS). |

### Транспорт и браузер
| ID | Правило |
|---|---|
| R-SEC-20 | Только HTTPS (локально — доверенный сертификат); HSTS при публикации в интернет. |
| R-SEC-21 | Заголовки: CSP без `unsafe-inline` (nonce или хеши), `nosniff`, `Referrer-Policy`, запрет встраивания (`frame-ancestors 'none'`), минимальная `Permissions-Policy`. |
| R-SEC-22 | CORS — только собственный источник; куки не уходят на чужие. |
| R-SEC-23 | CSRF: токен на всех изменяющих запросах + проверка `Origin` + SameSite. |
| R-SEC-24 | Личные и служебные страницы: `Cache-Control: no-store`. |

### Защита данных
| ID | Правило |
|---|---|
| R-SEC-25 | **Шифрование в канале** — TLS; **на диске** — средствами ОС/СУБД **[проверить в Фазе 7]**; **на уровне приложения** — секреты TOTP, email (шифр + слепой индекс HMAC для поиска) **[ГИПОТЕЗА]**. |
| R-SEC-26 | Ключи вне репозитория, раздельные для сессий, шифрования, HMAC; план ротации. |
| R-SEC-27 | Минимизация: собираем только нужное; IP в логах и аналитике усечён; аналитика псевдонимизирована (`ANALYTICS`). |
| R-SEC-28 | Права субъекта данных: экспорт и удаление с анонимизацией (OP-16); сроки хранения — §4. |
| R-SEC-29 | Логи без паролей, токенов и полного текста материалов; сквозной идентификатор запроса; переводы строк экранируются (нет подмены записей). |
| R-SEC-30 | Резервные копии: по расписанию, зашифрованы отдельным ключом, хранятся отдельно от БД, раз в месяц — проверка восстановления **[ГИПОТЕЗА RPO 24 ч, RTO 2 ч]**. |

### Злоупотребления и доступность
| ID | Правило |
|---|---|
| R-SEC-31 | Лимиты по классам: вход, регистрация, отправка материалов, поиск, чтение API, импорт; ответ 429 с `Retry-After`; отдельные лимиты для гостей. |
| R-SEC-32 | Потоки реального времени: потолок соединений на пользователя; таймауты запросов; пагинация с верхней границей (limit ≤ 100). |
| R-SEC-33 | Антиспам модерации — `MODERATION`. |
| R-SEC-34 | Вместо картиночной CAPTCHA — proof-of-work или невидимая проверка (доступность, `A11Y`). |

### Админ-зона
| ID | Правило |
|---|---|
| R-SEC-35 | `/admin`, `/mod`, `/analytics`: роль + 2FA + короткая сессия; отдельные лимиты; ответ 404 вместо 403 для неавторизованных **[ГИПОТЕЗА]**. |
| R-SEC-36 | Журнал аудита только на добавление: у приложения нет прав на изменение и удаление записей; пишется при каждом действии админа и редактора. |
| R-SEC-37 | Последний админ защищён от понижения, бана и удаления. |

### Цепочка поставок и эксплуатация
| ID | Правило |
|---|---|
| R-SEC-38 | Lock-файл; аудит зависимостей в CI; минимальный набор пакетов; новые пакеты — с обоснованием. |
| R-SEC-39 | Сканер секретов в CI и по истории git; ключ TMDB и пароли БД только в окружении. |
| R-SEC-40 | Режим отладки выключен; конфигурация проверяется при старте; обязательные переменные заданы или приложение не запускается. |
| R-SEC-41 | Единый формат ошибок без трассировок и путей; детали — только в журнале. |
| R-SEC-42 | БД: отдельный пользователь с минимальными правами, недоступна снаружи, шифрованное соединение. |

## 4. Сроки хранения **[ГИПОТЕЗА]**

| Данные | Срок |
|---|---|
| Сессии | до истечения + 7 дней в журнале |
| Токены сброса и подтверждения | до использования или истечения |
| Сырые события аналитики | 90 дней; агрегаты бессрочно |
| Журнал аудита | не менее 1 года, без удаления |
| Отклонённые материалы | 30 дней, затем удаление |
| Резервные копии | 30 ежедневных + 6 ежемесячных |
| Аккаунт после запроса удаления | 14 дней на отмену, затем анонимизация |

## 5. Проверка

Автоматически: матрица прав из `ROLES-PERMISSIONS` (каждый маршрут × роль), корпус XSS-нагрузок на каждом поле материалов, SQL-инъекции в фильтрах и поиске, SSRF-загрузчик, лимиты, заголовки, сканер секретов, аудит зависимостей. Вручную перед защитой — чек-лист из `PRODUCTION-READINESS`.

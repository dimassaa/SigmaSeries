# RETENTION — что сколько живёт и что удаляется

> v0.1 · Фаза 5 · закрывает `SECURITY` §4 и часть требования Бланка 3.3.4 (защита хранимых данных).
> **Правило, из которого выведены все числа:** у каждой категории данных есть срок, и срок задан не «чтобы было аккуратно», а по одной из трёх причин — юридическое требование, требование безопасности или отсутствие смысла хранить.

## 2. Правила, которые важнее чисел

1. **Удаление — это анонимизация, а не стирание строки.** Для пользователя, материалов и решений. Причина — требование ссылочной целостности (Бланк 3.3.1) и `M9` §0.
2. **Непроверенная резервная копия не удаляется никогда.** Это самое неочевидное правило документа, и оно противоположно интуиции: «неудачную копию вычистим». Если удалять, то после серии неудачных проверок не останется ни одной годной копии.
3. **Агрегаты бессрочны, сырьё — нет.** Так срок 90 дней применяется к чувствительным данным, а дешёвые обезличенные сравнения доступны за весь период работы сервиса.
4. **Ни одна задача очистки не удаляет то, что не записано явно в этой таблице.** Новый вид данных по умолчанию живёт вечно — и это ошибка, которую надо заметить на ревью, а не при обработке.
5. **Очистка пишет в аудит.** Сама операция удаления — действие, и она видна в журнале как и любая другая.

## 3. Кто отвечает

| Задача | Периодичность | Что делает |
|---|---|---|
| Очистка сессий | ежедневно | удаляет отозванные старше 30 дней |
| Очистка писем | ежедневно | удаляет старше 180 дней |
| Очистка событий | ежедневно | удаляет старше 90 дней, сохраняя агрегаты |
| Очистка экспортов | ежедневно | удаляет файлы старше суток |
| Проверка истечения ролей | ежедневно | снимает просроченные роли, пишет в аудит |
| Проверка истечения ограничений | ежедневно | снимает истёкшие мьюты, разблокирует отправку |
| Ротация резервных копий | после успешной новой копии | удаляет копии старше 7, **только проверенные** |
| Ротация логов | при заполнении | по размеру файла |

Все задачи — **до** резервного копирования (M9 F-09-04 правило (в)): сначала очистка, потом дамп, чтобы в копии не попало то, что уже удалено.

## 4. Проверка

1. Через 91 день сырых событий в базе нет, агрегаты за тот период — есть.
2. Копия, созданная с ошибкой проверки, присутствует через любой срок.
3. После анонимизации пользователя его `e_watch_mark` пусты, а `e_material` — сохранены и обезличены.
4. Каждая задача очистки оставила запись в `e_audit_log`.
5. Ни одна задача не удалила строку, не перечисленную в §1.

# ARCHITECTURE — архитектурные решения

> v0.1 · Фаза 7 · закрывает ПЗ 4.2.3 «Архитектурные решения» и 4.2.1 «Постановка задачи». Опирается на `STACK.md`, `DATABASE.md`, `M0-shell`, `M2-catalog` F-02-11, `SECURITY`.
> Каждое решение записано как ADR и живёт отдельным файлом в `adr/`. Здесь — сводка и то, что не помещается в отдельные решения.

## 1. Модель приложения

**MVC, а не MVP.** Решение `adr/ADR-001-mvc-over-mvp.md`.

Бланк допускает обе. Разница практическая: в MVP представление не знает о модели, и при 60 экранах это означает дублирование правил отображения в каждом представлении — а правил много (частые валютные форматы, спойлеры, локальная дата, три рейтинга). В MVC правило лежит в модели, представление форматирует. Плата — контроллеры толще; приемлемо.

**Три слоя:**

```
┌──────────────────────────────────────────────────────────────┐
│  Маршруты Express (тонкие: разбор, проверка, вызов сервиса)  │
└───────────────────────────────┬──────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────┐
│  Сервисы — вся бизнес-логика, ЗДЕСЬ живут OP-01…OP-17          │
│  модерация · рейтинг · календарь · уведомления · импорт …     │
└───────────────────────────────┬──────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────┐
│  Доступ к данным — запросы SQL, только здесь                  │
└───────────────────────────────┬──────────────────────────────┘
                                │
                        ┌───────▼────────┐
                        │   PostgreSQL   │
                        └────────────────┘
```

**Правило, из которого следует всё остальное:** маршрут не содержит логики, сервис не знает про HTTP, слой данных не знает ни про что. Проверяется это просто — невозможно написать тест на сервис, если он читает `req`. Это и есть требование Бланка 3.3.1 «бизнес-логика реализует основные алгоритмы обработки данных»: алгоритмы находятся в именованных функциях, а не размазаны по обработчикам.

## 2. Рендеринг: серверные страницы

**Решение `adr/ADR-002-server-rendering.md`.**

Основной вариант — серверный рендеринг шаблонов с клиентским JavaScript поверх, а не SPA с клиентским роутингом.

Причины, в порядке веса:

1. **SEO.** 60 экранов, из них индексируемых около 40. При SPA содержимое появляется после выполнения скрипта, и часть поисковиков индексирует пустую оболочку. Требование SEO не факультативно.
2. **Бланк 3.2** прямо перечисляет HTML, DHTML и гиперссылки как способ навигации. SPA с клиентским роутингом формально подходит, но серверные страницы следуют требованию буквально.
3. **Защита на очной защите.** Серверные страницы работают всегда: нет зависимости от того, что клиентский скрипт загрузился.
4. **LCP ≤ 2,5 с** достигается проще: контент в первом байте ответа, а не после загрузки бандла.

Интерактивность обеспечивается точечно: rail (M0 F-00-01), карточка постера (M2 UI-10), карусель новинок (M6 F-06-03), бегущая строка (M6 F-06-04), модальные окна. Каждая из них — небольшой модуль, а не приложение целиком.

**Цена решения признаётся честно:** дублирование разметки между серверным шаблоном и клиентским обновлением в пяти местах; медленнее ощущается навигация между страницами. Это компромисс в пользу индексации и надёжности на защите.

## 3. Слои и что где живёт

| Слой | Что содержит | Чего не содержит |
|---|---|---|
| **Маршруты** | Разбор параметров, проверка (`zod`), проверка прав по сессии, вызов сервиса, выбор шаблона, код ответа | Бизнес-правил, SQL, форматирования |
| **Сервисы** | OP-01…OP-17, правила домена, вычисление рейтинга, календаря, состояния выхода | `req`/`res`, HTTP-кодов, SQL |
| **Данные** | SQL, маппинг строк в объекты | Правил домена, знания о пользователе |
| **Шаблоны** | Разметка, классы, подстановка подготовленных значений | Логики; условия вида «показать, если» допускаются, вычисления — нет |

## 4. Локализация и адреса

**Решение `adr/ADR-003-locale-in-path.md`.**

- Адрес имеет вид `/{locale}/…`, где `locale` — `ru` или `en` по умолчанию. Без префикса — 301 на `/ru/…`.
- Язык по умолчанию `ru` **всегда**, независимо от `Accept-Language`: проект русскоязычный, и автоопределение по браузеру уводило бы англоязычного пользователя в английский интерфейс с русским контентом.
- Переключение языка сохраняет текущий путь и полосу прокрутки (M0 F-00-02).
- `hreflang` для пары `ru`/`en` плюс `x-default` на русский.
- Интерфейсные строки — в словаре, ключи `shell.*`, `nav.*`, `home.*`, `ugc.*` и далее по модулям. **Пользовательский текст не переводится** (M5 §0).

**Ожидаемый отказ:** если руководитель запретит английский (письмо, п. 2), решение пересматривается: префикс локали уходит, `I18N` сокращается с 17 правил до примерно пяти, `hreflang`-правила `SEO` удаляются. Оценка этой работы — 2–3 дня, поэтому письмо отправляется до начала кода.

## 5. Задачи по расписанию

**Решение `adr/ADR-004-in-process-scheduler.md`.**

Планировщик — `node-cron` внутри того же процесса, без внешнего планировщика и без очередей. Пять задач: `schedule_sync`, `discover_sync`, `ratings_sync`, `full_run`, ежедневная ротация и уборка.

Почему не внешний планировщик: задач пять, они не требуют независимости от веба, и добавление ещё одного сервиса в проект, где по Бланку нет права на неagreсованные инструменты, потребовало бы согласования.

Что из этого следует и что надо помнить: **задачи не выживут перезапуск процесса.** Поэтому каждая задача проверяет «не просочился ли я» при старте (`M3` F-03-07 правило (а): если последний успешный `schedule_sync` старше 36 часов — запустить немедленно). Это поведение описано в спеках и теперь обосновано.

Порядок ночью: **резервная копия → очистка → синхронизация расписания → открытие новых → рейтинги.** Резервная копия первая, чтобы в копию не попало то, что уже удалено (RETENTION §3).

Такт ежеминутный, а «пора ли» решает планировщик по `import.schedule_time`: время из настроек меняется без перезапуска приложения, и cron-выражение, зарегистрированное один раз, разошлось бы с настройкой. Блокировка запуска — в базе, а не в памяти процесса: после перезапуска память пуста, и ночь легла бы поверх полного прогона, запущенного вручную.

Рейтинги идут раз в неделю — понедельник, час после ночного запуска (`DEC-053`); отдельного ключа настроек нет, и это осознанное решение, а не забывчивость.

```mermaid
activityDiagram
    start
    :Такт: минута по node-cron или старт процесса;
    if (import.enabled = off) then (да)
        :Ничего не планируем и не запускаем: причина «выключено»;
    else (нет)
        if (включён режим защиты?) then (да)
            :Ничего не планируем: причина «защита»;
        else (нет)
            if (старт процесса и успеха нет дольше 36 ч?) then (да)
                :Создаём просроченный план расписания на сейчас;
            else (нет)
            end
            :Планируем ближайшие вхождения задач: расписание и рейтинги;
            if (пора расписанию?) then (да)
                if (прогон уже идёт?) then (да)
                    :Записываем пропуск: расписание и обзор новых следом;
                else (нет)
                    :planned → running: синхронизация расписания;
                    if (расписание упало?) then (да)
                        :Обзор новых не идёт, прогон закрыт ошибкой;
                    else (нет)
                        if (пора обзору?) then (да)
                            :planned → running: открытие новых сериалов;
                        else (нет)
                        end
                    end
                end
            else (нет)
            end
            if (пора рейтингам, раз в неделю?) then (да)
                if (прогон уже идёт?) then (да)
                    :Записываем пропуск рейтингов;
                else (нет)
                    :planned → running: рейтинги из датасета IMDb;
                end
            else (нет)
            end
        end
    end
    stop
```

## 5.1. Просмотр календаря

Календарь — единственный экран, где решение человека меняет результат запроса, поэтому порядок шагов в нём зафиксирован (OP-08, `F-03-05` §8).

**Пояс раньше дат.** Пояс посетителя лежит в cookie (`tz`), которую ставит скрипт браузера из `Intl`. Пока cookie нет — `Europe/Minsk` (H-72). Проверка по списку поясов среды, а не по попытке формата: мусор в cookie иначе превращал бы `formatToParts` в исключение на каждом запросе. Дата хранится UTC (M3 §0), и это другое число, чем пояс: путать их — значит сдвинуть весь каталог на шесть часов.

**Дата важнее статуса.** В календарь попадает любой выход видимого сериала, чья дата лежит в диапазоне, — независимо от того, «выходит» сериал или «ждёт сезон» (H-39). Обратное правило (фильтровать по состоянию) сделало бы календарь пустым накануне премьеры.

**Точность решает, сдвигается ли день.** Выход с точностью «дата» в поясе посетителя остаётся на своей дате: сдвигать его на шесть часов назад нельзя. Выход с точностью «дата и время» пересчитывается и может перейти на соседний день (EC-T3). Смещение пояса считается через `Intl` — свой пересчёт летнего времени был бы второй, неверной реализацией.

**Выход — это группа серий с одной датой**, а не строка в календаре (EC-D11): восемь серий, вышедших в один день, — одна запись «8 серий», а не восемь точек в одном дне.

```mermaid
activityDiagram
    start
    :Пояс из cookie tz, иначе Europe/Minsk;
    :Сегодня посетителя — его, а не сервера;
    :Разбор адреса: вид, фильтр, месяц, день — по белому списку;
    if (фильтр «Мои» и посетитель гость?) then (да)
        :Приглашение войти вместо пустой сетки (EC-T21);
    else (нет)
        :Диапазон: день, неделя или месяц, не длиннее предела;
        :Выходы видимых сериалов за период — один запрос;
        if (точность «дата и время»?) then (да)
            :Пересчитать момент в пояс посетителя: день может смениться;
        else (нет)
            :День остаётся датой из базы (OP-08а);
        end
        :Сгруппировать по дням, внутри дня — время, затем название;
        if (в ячейке больше трёх записей?) then (да)
            :Показать три и «+N» — ссылку на список дня (EC-T15);
        else (нет)
        end
        if (месяц текущий ± 1?) then (да)
            :Страница индексируется;
        else (нет)
            :noindex: таких адресов десятки тысяч (R-SEO-02);
        end
    end
    stop
```

## 6. Изображения

**Решение `adr/ADR-005-images-in-database.md`.**

Изображения хранятся в БД (`C-04`, подтверждено DEC-014) и отдаются через маршрут с кэш-заголовками.

- Оригиналы и варианты 185/342/500 по ширине для постеров, 780/1280/1920 для фонов (M12 F-12-05).
- Ответ: `Cache-Control: public, max-age=31536000, immutable` — имя файла содержит хеш содержимого, значит содержимое неизменно и кэш безопасен.
- Отдаёт **первое попадание по варианту**, а не клиент: `w`, `h`, `fit`, `dpr` в параметрах; браузер получает нужное, а не то, что просил отдать.
- Размер базы ≈ 1,4 ГБ на 1197 сериалов — измерено, `DATA-SOURCES` §10.

**Цена решения:** 1,4 ГБ в бэкапе снимаются при каждом копировании, и `pg_dump` такой базы работает медленно, чем у БД с файлами. Это принято: преимущество — офлайн-демонстрация на защите без внешнего сервиса, а это требование C-12.

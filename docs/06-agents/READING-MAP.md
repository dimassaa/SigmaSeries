# READING-MAP — что читать под каждую задачу

> v0.1 · Фаза 8 · закрывает вторую часть набора для агента. Правило простое: **читать мало и точно**. Агент на длинном контексте забывает и выдумывает; проект — 40 документов, полное чтение которых бессмысленно и дорого.
> **Перед любой задачей:** `docs/STATUS.md` (одна страница: где мы, что решено, что открыто). Это единственный документ, который нужно держать в голове целиком.

## 1. Порядок по типу задачи

| Тип задачи | Сначала | Потом | Проверить |
|---|---|---|---|
| **Реализация фичи** | `/pack F-01-03` | §14 пакета — «Куда смотреть дальше» | Приёмка фичи, `M4` §3 |
| **Реализация по экрану** | `/pack F-02-01`, затем `SCREENS` §правила | `PRINCIPLES`, `TOKENS`, `COMPONENTS` | Клавиатура, светлая и тёмная темы, псевдолокаль |
| **Импорт данных** | `/pack F-12-06` | `DATA-SOURCES` §2, §5 | Счётчики отчёта совпадают с ожиданием |
| **Модерация** | `/pack F-05-02` | `MODERATION` §1, §3 | Каждая ветвь блок-схемы покрыта тестом |
| **Безопасность** | `/pack F-01-08` | `SECURITY` §2, `THREAT-MODEL` | Тест на каждое затронутое `R-SEC` |
| **Админка** | `/pack F-09-02` | `ROLES-PERMISSIONS` §2 | Клетка матрицы прав не пропущена |
| **Вопрос «где определено X»** | `/where R-SEC-04` | — | — |
| **«Что изменится, если…»** | `/neighbors F-03-08` | `/module M3` | — |
| **Новая фича** | `/module M4` + соседние фичи | `PLAN` §5 (шаблон) | Шаблон соблюдён, иначе пакет не соберётся |

## 2. Что читать целиком, а что — по требованию

**Целиком, всегда:** `README.md`, `docs/STATUS.md`. Это ~250 строк, они держат проект в голове.

**По требованию:** всё остальное. Ни один документ не читается «для ознакомления» — читается раздел, нужный задаче.

**Никогда не читать целиком:** `EDGE-CASES` (230 строк, ссылайся по ID), `FEATURES`, `COVERAGE`, `SCREENS` целиком (нужен один экран), `MODULES` целиком (нужен один модуль).

## 3. Три пакета, которые нужны чаще всего

| Пакет | Когда |
|---|---|
| `/pack F-00-01` | Любая работа с оболочкой, rail, навигацией, раскладкой |
| `/pack F-03-05` | Календарь, даты, локальное время — источник половины «непонятных» багов |
| `/pack F-12-06` | Импорт, состояние выхода, «Выходит» против «Ждём сезон» |

## 4. Правила, которые экономят больше всего

1. **Числа и пороги — только из таблиц настроек модуля.** Не из памяти, не из соседней фичи. У каждой настройки есть ключ; если его нет в таблице — это находка, а не повод придумать значение.
2. **Правило живёт в стандарте, ссылка — в фиче.** Не копировать текст правила в код: он разъедется при первой правке.
3. **Один ID определён в одном месте.** Если правило встречается в двух файлах — одно из них устарело; ищи определение через `/where`.
4. **`[ГИПОТЕЗА]` — это не утверждение.** Значение под меткой нельзя принимать за согласованное; оно меняемо по одной команде от автора.
5. **Не читать спеки соседних модулей «для контекста».** Контекст даёт `--neighbors`.

## 5. Порядок чтения при входе в новую сессию

1. `README.md` — что это и что где.
2. `docs/STATUS.md` — где мы и что открыто.
3. `git log --oneline -5` — что менялось в последние дни.
4. `/check` — есть ли битые ссылки и превышения размера пакета.
5. Задача → пакет по таблице §1.

Пункты 4 и 5 необязательны только если задача — правка текста документа, а не кода.

## 6. Что делать, если нужного документа нет

Ничего не придумывать. Проверить по порядку:

1. Нет ли его в `PLAN` §7 или §11 среди ненаписанных (`GLOSSARY`, `ROLES-PERMISSIONS` написаны; `AGENTS` — этот набор).
2. Нет ли нужного внутри пакета соседней фичи.
3. Нет ли в `DECISIONS` — там решения автора, включая те, что ещё не оформлены в правила.

Если нет во всех трёх — **это блокер, эскалация L3**. Не «решим по ходу»: цена такого решения обнаруживается на защите, а не при написании кода.
